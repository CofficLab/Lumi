# 方案:StepFun 供应商探测可用后再注册子Agent(异步网络探测)

## 现状与核心矛盾
- `StepFunPlugin.subAgents(kernel:)` 目前无条件返回全部 7 个子Agent,无任何 gate。
- 该方法是**同步**协议方法,框架只在 boot(`registerAgentTools`)/插件开关(`rebuildAllContributions`)时调用,且无事件机制让插件运行时触发自己的重新收集——除非插件主动调 public 的 `kernel.pluginManager.rebuildAllContributions(in:)`。
- 可用性是**异步网络探测**(`checkAvailability`,带 5 分钟磁盘缓存)。
- boot 时序:`onReady`(步骤3)→ `registerAgentTools` 调 `subAgents`(步骤5)→ `registerLLMProviders` 注册 provider(步骤7)。即 `subAgents` 被调时 provider 还没进 kernel registry。
- 现有 `StepFunSubAgentsGateTests.swift` 引用的 `subAgents(context:)` / `LumiPluginContext` 已被重构删除,**无法编译**,实际是一份未实现的规格说明。
- (附带发现)`StepFunProvider.providerStatus()` 当前是无限递归 bug,本方案**绕过**它(用网络探测而非 status),不在本次范围内修复。

## 设计:同步 gate + 异步探测 + 探测后触发重建

新增一个 `@MainActor` 状态机 `StepFunSubAgentsGate`,插件持有单例 provider 实例(不再依赖 kernel registry):

```
状态机:  unknown(初始) ──探测通过──▶ ready   → subAgents 返回全部 7 个
              │
              └──探测失败──▶ unavailable        → subAgents 返回 []
          (unknown 也返回 [],保守 gate)
```

1. **provider 实例由插件自己持有**(改为 lazy 存储属性,而非每次 `llmProviders()` new),规避 boot 时序问题——`subAgents` 在任何时点都能直接访问自己的 provider 去探测,不查 kernel registry。
2. **同步 gate**:`subAgents(kernel:)` 内仅根据 gate 当前状态返回 `[全部]` 或 `[]`,满足同步签名。
3. **异步探测**:在 `onReady(kernel:)` 里启动一个后台 `Task { @MainActor in ... }`(不阻塞 startup),调 `provider.checkAvailability(model: "step-3.7-flash")`(子Agent 实际依赖的模型;复用现有 `AvailabilityDiskCache`,命中缓存几乎立即返回)。
4. **探测后触发重建**:状态从 `unknown→ready` 时,调一次 `kernel.pluginManager.rebuildAllContributions(in: kernel)`(public),让框架重新收集 `subAgents`,此时 gate 已 ready → 子Agent 被注册。仅此一次,成本可接受(全量重建,无更细粒度公开 API)。

时序自洽:`onReady` 异步启动探测 → 随后 `registerAgentTools` 调 `subAgents`(此时探测未完 → 返空,gate)→ 探测完成 → 触发 rebuild → 重新调 `subAgents`(已 ready → 返全部)。磁盘缓存命中时,从启动到注册成功的窗口被压到很短。

## 具体文件改动

### 1. 新建 `Sources/SubAgents/StepFunSubAgentsGate.swift`
`@MainActor final class`,持有探测状态枚举 + 当前可用性结果。提供:
- `func evaluate(kernel:) -> [LumiSubAgentDefinition]`(同步读状态:ready 返全部,否则空)
- `func refresh(kernel:) async`(异步探测;探测后按需触发 rebuild)
- 一个静态的"全部子Agent 定义"集合(从现有 7 个 `*.definition` 聚合,消除重复)

### 2. 改造 `Sources/StepFunPlugin.swift`
- 新增 `private let provider = StepFunProvider(...)`(或 lazy),`llmProviders(kernel:)` 返回它;`subAgents(kernel:)` 委托给 `gate.evaluate(kernel:)`。
- 新增 `private let gate = StepFunSubAgentsGate(provider: provider)`。
- `onReady(kernel:)` 中启动后台探测 `await gate.refresh(kernel: kernel)`(用 Task 包裹,不阻塞)。

### 3. 重写 `Tests/StepFunSubAgentsGateTests.swift`
现有文件无法编译(引用已删除 API)。重写为针对**同步状态机**的可编译测试:
- 注入可控状态,断言 ready→全部7个、unknown/unavailable→空。
- 用可注入的 provider 协议抽象(或直接用真实 provider 的 `checkAvailability` 但 stub 网络)验证"探测通过→ready→触发 rebuild"路径。
- 删除对 `LumiPluginContext` / `subAgents(context:)` 的依赖,改测 `gate.evaluate` / `StepFunPlugin().subAgents(kernel:)`。
- 同时修正 `PluginLLMProviderStepFunTests.swift` 中 `StepFunPlugin.name` / `StepFunProvider.name` 的静态误用(改为实例访问 `.name` / `StepFunProvider.info.*`),使该 target 在 `swift test` 下可编译。

## 边界与取舍(默认值,可调整)
- **首版探测策略**:仅 `onReady` 探测一次,复用磁盘缓存。探测失败后保持 gate,直到下次插件开关(触发 `rebuildAllContributions` 自然重试)或重启。不做轮询/重试/订阅 API Key 变化(框架无此信号,且超出本次需求)。
- **触发重建用全量 `rebuildAllContributions`**:仅"首次 unknown→ready"时触发一次,影响可接受;无更细粒度公开 API。
- **探测模型**:用 `step-3.7-flash`(子Agent 实际依赖的模型)。
- **不修复** `providerStatus()` 无限递归 bug(与本次需求无关,避免扩大范围;会单独提示)。

## 验证
- `swift build` 通过(插件包)。
- `swift test` 通过:gate 状态机 3 个核心用例 + 探测→ready→rebuild 路径。
- 手动验证:清空 StepFun API Key → 子Agent 不出现;配置 Key 并探测通过 → 子Agent 出现。
